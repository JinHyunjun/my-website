02 · Selection Criteria

“쉬워 보인다”보다 중요한 네 가지 기준

초보자의 첫 기여는 코드 줄 수가 아니라 재현성, 범위, 선례, 중복 여부로 판단해야 했습니다.

01

직접 재현 가능한가

CLI나 기존 테스트로 현재 동작과 기대 결과를 확인할 수 있어야 합니다.

02

변경 범위가 작은가

파일 수와 책임 경계를 설명할 수 있는 크기로 시작합니다.

03

따라갈 선례가 있는가

비슷한 테스트나 문서가 있어 프로젝트 방식을 배울 수 있어야 합니다.

04

다른 작업과 겹치지 않는가

Assignee, 댓글, 연결 PR, 같은 파일을 만지는 활성 PR을 확인합니다.

good first issue 라벨만 보고 고르면 이미 누군가 진행 의사를 남겼거나 실제 구현 범위가 넓을 수 있습니다. 그래서 제가 직접 재현할 수 있는지, 변경 파일을 설명할 수 있는지, 기존 예제가 있는지, 현재 누가 작업 중인지 네 가지를 기준으로 삼았습니다.

03 · Contribution Landscape

GlueSQL 기여는 한 종류가 아니라 난이도 경사가 있다

첫 PR은 가장 왼쪽에서 시작해도 충분합니다. 중요한 것은 테스트와 문서가 실제 코드 동작을 근거로 한다는 점입니다.

ENTRY 1

문서 보완

현재 Todo 페이지를 실제 API와 테스트 결과에 맞게 설명합니다.

ENTRY 2

테스트·예제 추가

기존 패턴을 따라 지원 동작과 오류 경계를 실행 가능한 사례로 남깁니다.

ENTRY 3

Fixture 도구 개선

테스트 문법, assertion, parser 규칙과 호환성을 함께 다룹니다.

ENTRY 4

Core 기능 변경

Translator·Planner·Executor의 계약과 여러 Storage에 미치는 영향을 검증합니다.

문서와 테스트는 코어보다 덜 중요한 일이 아니라, 동작을 이해했다는 검증 가능한 결과다.
GlueSQL에는 문서, 테스트, fixture 도구, 코어 기능처럼 여러 기여 층이 있습니다. 초보자에게 문서와 테스트가 좋은 이유는 쉬워서만이 아닙니다. 구현을 읽고 실제 결과를 확인해야 정확하게 쓸 수 있기 때문에 구조를 배우는 입구가 됩니다.

07 · Architecture Payoff

이 후보는 두 번째 실행 입구를 보여준다

SQL 문자열과 Query Builder는 같은 실행기로 향하지만, 앞부분의 경로가 다릅니다.

SQL TEXT
Parser
Translator
StatementPlan
Storage Planner
Executor → Payload
QUERY BUILDER
Rust Builder API
Parser·Translator
Build → StatementPlan
Storage Planner
Executor → Payload
첫 기여 후보가 곧 다음 학습 주제다. Query Builder가 SQL 문자열 경로를 어떻게 우회하는지 코드로 확인할 수 있다.
제가 지금까지 배운 Parser, Translator 경로만이 GlueSQL의 전부는 아닙니다. Query Builder의 Execute trait은 Build로 StatementPlan을 만든 뒤 storage.plan과 execute_stmt로 갑니다. 그래서 이 문서 테스트는 코어를 크게 바꾸지 않으면서 GlueSQL의 두 번째 입력 경로를 배우게 해 줍니다.

09 · Five-Step Trial

발표 뒤에 진행할 작은 완주 루프

첫 목표는 PR이 아니라, 이 후보가 정말 내 수준과 프로젝트 방향에 맞는지 검증하는 것입니다.

01 · RUN

기존 values 테스트 실행

현재 API와 Payload 형태를 로컬에서 확인합니다.

02 · READ

완성 문서 비교

Data Aggregation 문서와 테스트의 연결 방식을 읽습니다.

03 · DEFINE

최소 예제 정의

VALUES 입력, 실행 결과, 설명 범위를 한 문장으로 정합니다.

04 · ASK

Maintainer 확인

#1676에 하위 항목 범위와 중복 여부를 질문합니다.

05 · DECIDE

진행 또는 전환

합의되면 구현하고, 겹치면 #1408의 작은 조사로 전환합니다.

중단 기준도 정한다. 범위가 커지거나 코어 변경이 필요하면 다시 쪼개고 질문한다.
다음 행동은 구체적입니다. 기존 values 테스트를 실행하고, 완성된 Data Aggregation 문서를 비교하고, 최소 예제를 정의합니다. 그 뒤에 Maintainer에게 묻습니다. 가능하면 기여 브랜치를 만들고, 겹치거나 범위가 커지면 Storage 문서 조사의 작은 단위로 전환합니다.
