02 · What I Learned

SQL 한 줄은 역할이 나뉜 단계를 통과한다

Core는 SQL을 실행 가능한 계획으로 바꾸고, 선택된 Storage의 계약을 통해 데이터를 읽거나 바꿉니다.

INPUTSQL사용자가 전달한 문자열
01ParserSQL을 AST로 구조화
02TranslatorAST를 GlueSQL 문장으로 변환
03PlannerStorage와 실행할 계획 생성
04Executor계획에 따라 연산 수행
05Storage스키마와 행을 제공·변경
OUTPUTPayload조회 결과나 변경 건수 반환
Storage는 SELECT 결과를 쌓는 곳이 아니라, 실행 중 읽고 변경하는 원본 데이터 계층이다.
제가 이해한 전체 흐름은 SQL, Parser, Translator, Planner, Executor, Storage, Payload입니다. 여기서 중요한 수정은 Storage를 SELECT 결과 보관소로 이해하지 않는 것입니다. Storage는 스키마와 원본 행을 제공하고 INSERT나 UPDATE 같은 변경을 반영합니다. 실행 결과는 Payload로 호출자에게 돌아갑니다. 03 · The Turning Point

같은 SQL인데 재실행 결과가 달랐다

테이블이 사라진 경험이 Storage를 더 알고 싶은 구체적인 계기가 됐습니다.

MEMORY STORAGE

프로세스를 종료하자 테이블이 사라졌다

  • 별도 경로 없이 바로 실행
  • CLI 프로세스의 메모리에만 존재
  • 새 프로세스는 새 Storage로 시작
cargo run --locked -p gluesql-cli
SLED STORAGE

같은 경로로 다시 열자 데이터가 남아 있었다

  • --storage sled로 구현 선택
  • --path로 데이터 위치 지정
  • 종료 후 같은 경로에서 다시 조회
cargo run --locked -p gluesql-cli -- --storage sled --path .codex-local/study-sled
컴파일 결과인 target/과 실제 DB 데이터는 서로 다른 생명주기를 가진다.
Storage에 관심을 갖게 된 직접적인 계기입니다. 기본 CLI는 MemoryStorage를 사용하므로 종료 뒤 다시 실행하면 새 인스턴스가 만들어집니다. 반면 SledStorage는 경로를 지정하고 같은 경로로 다시 열었을 때 데이터가 남았습니다. 이때 target 폴더의 실행 파일과 DB 데이터가 별개라는 점도 이해했습니다. 실행 파일을 다시 빌드해도 데이터 보존 여부는 Storage와 데이터 경로가 결정합니다. [Sources] https://github.com/gluesql/gluesql/blob/main/cli/src/lib.rs · https://github.com/gluesql/gluesql/tree/main/storages/sled-storage

04 · Storage Contract

Core와 Storage는 Rust trait으로 연결된다

Core는 특정 DB 파일 형식을 직접 알기보다, 필요한 동작을 인터페이스로 요청합니다.

계약대표 메서드실행에서 하는 일
Storefetch_schema · fetch_data · scan_data테이블 구조와 행을 읽어 SELECT에 필요한 데이터를 제공
StoreMutappend_data · insert_data · delete_dataINSERT, UPDATE, DELETE에서 행 변경을 Storage에 반영
GStoreStore + Index + Metadata + Function조회에 필요한 여러 읽기 기능을 하나의 경계로 묶음
GStoreMutStoreMut + AlterTable + Transaction + ...쓰기, 스키마 변경, 트랜잭션 등 가변 기능을 묶음
Storage를 바꿔도 SQL Core를 재사용할 수 있는 이유는 구현보다 계약에 의존하기 때문이다.
코드에서는 core/src/store.rs가 핵심입니다. Store는 스키마와 데이터를 읽는 메서드를, StoreMut은 데이터를 추가하거나 삭제하는 메서드를 정의합니다. GStore와 GStoreMut은 Index, Metadata, Transaction 같은 여러 trait을 조합합니다. 각 Storage가 이 계약을 구현하기 때문에 Core는 Memory인지 Sled인지에 강하게 묶이지 않고 같은 SQL 실행 흐름을 재사용할 수 있습니다. [Sources] https://github.com/gluesql/gluesql/blob/main/core/src/store.rs

05 · Why Choice Matters

Storage 선택은 이름이 아니라 요구사항의 조합이다

“무엇이 가장 좋은가?”보다 “이 상황에서 무엇이 필요한가?”를 먼저 물어야 합니다.

01

데이터를 얼마나 오래 남길 것인가

한 프로세스 안의 임시 데이터인지, 재시작 이후에도 보존할 데이터인지 구분합니다.

02

어디에서 실행할 것인가

브라우저, 단일 로컬 앱, 여러 스레드, 외부 서비스 등 실행 환경을 봅니다.

03

어떤 형식과 연결할 것인가

JSON, CSV, Parquet처럼 이미 존재하는 파일과 SQL을 연결할 필요가 있는지 봅니다.

04

어떤 기능을 보장해야 하는가

인덱스, 트랜잭션, 스키마 변경처럼 필요한 trait과 실제 지원 범위를 확인합니다.

Storage를 선택할 때는 단순 속도 순위로 볼 수 없다고 생각합니다. 데이터가 재시작 후에도 남아야 하는지, 어디에서 실행할지, 기존 파일 형식과 연결해야 하는지, 인덱스나 트랜잭션 같은 기능이 필요한지를 함께 봐야 합니다. 이 기준별로 실제 구현과 테스트를 확인하는 것이 제 다음 학습 질문입니다. [Sources] https://gluesql.org/docs/latest/storages/

06 · Storage Landscape

저장 방식이 달라지면 사용 장면도 달라진다

현재 저장소에는 12개 Storage crate가 있고, CLI는 그중 7개를 직접 선택할 수 있습니다.

분류Storage먼저 확인할 질문
메모리memory · shared-memory임시 사용인가, 여러 스레드가 같은 데이터를 봐야 하는가
로컬 영속sled · redb · file프로세스 밖에 남겨야 하는가, 데이터 파일은 어떻게 관리되는가
파일 형식json · csv · parquet기존 파일을 SQL로 읽고 쓰는 목적이 있는가
외부 서비스mongo · redis이미 운영 중인 데이터 서비스와 연결하는가
조합·이력composite · git여러 Storage를 묶거나 변경 이력을 남겨야 하는가

storages 디렉터리에는 Memory, SharedMemory, Sled, Redb, File, JSON, CSV, Parquet, Mongo, Redis, Composite, Git의 12개 crate가 있습니다. 이 표는 우열을 정한 것이 아니라 탐색 질문별로 묶은 것입니다. 현재 CLI의 storage enum에서는 Memory, Sled, Redb, JSON, CSV, Parquet, File 일곱 종류를 직접 선택할 수 있습니다. 나머지는 라이브러리 수준에서 구성하거나 별도 환경이 필요합니다. 07 · My Interest

내가 더 알고 싶은 것은 데이터가 사는 방식이다

같은 SQL을 유지하면서, 사용 목적에 맞는 Storage를 어떻게 선택하고 검증할 수 있을까?

Storage 이름을 외우는 것보다 선택 근거와 실제 동작의 차이를 재현 가능한 형태로 남기고 싶습니다.

QUESTION 01

각 Storage는 데이터를 어디에, 어떤 형태로 남기는가?

QUESTION 02

같은 SQL에서 지원 기능과 오류 경계는 어떻게 달라지는가?

QUESTION 03

초보자가 사용 상황에 맞춰 선택할 수 있는 설명은 충분한가?

제 관심은 새로운 SQL 문법 자체보다 데이터가 실제로 어디에 남고, 같은 SQL을 여러 저장 방식에 어떻게 연결하는지에 있습니다. 특정 Storage 하나를 최고라고 정하려는 것은 아닙니다. 사용 목적에 따라 선택 기준을 세우고, 그 기준을 실제 실행과 코드로 검증한 뒤 다른 초보자도 따라 할 수 있는 형태로 정리하는 데 관심이 있습니다.

08 · Contribution Directions

문법 기여와 Storage 기여는 서로 다른 질문을 넓힌다

둘 중 하나가 더 중요한 것이 아니라, GlueSQL의 서로 다른 확장 지점을 다룹니다.

SQL SYNTAX · FUNCTIONS

무엇을 표현할 수 있는가

아직 구현되지 않은 SQL 문법이나 함수를 추가해 사용자가 작성할 수 있는 쿼리의 범위를 넓힙니다.

+
STORAGE · INTEGRATION

어디에서 어떻게 살게 할 것인가

같은 실행 Core를 다양한 데이터 형식과 저장 시스템에 연결하고, 선택과 검증의 기준을 분명하게 만듭니다.

현재의 나는 “새 문법”보다 “같은 SQL과 다른 Storage의 차이”에서 더 많은 질문이 생긴다.
팀원 중에는 GlueSQL에 아직 구현되지 않은 SQL 문법을 추가하는 데 관심이 있는 분들도 있습니다. 그 방향은 사용자가 표현할 수 있는 SQL 범위를 넓힙니다. 제가 관심을 가진 Storage 방향은 같은 Core를 어떤 데이터 계층에 연결하고, 그 선택을 어떻게 설명할지 다룹니다. 서로 경쟁하는 주제가 아니라 GlueSQL의 모듈성을 서로 다른 쪽에서 확장하는 기여라고 생각합니다.

09 · How I Want to Contribute

기능부터 만들기보다 비교 가능한 근거부터 만든다

작은 실험을 반복해 이해한 범위를 넓히고, 그 과정에서 문서·테스트·코드의 빈틈을 찾겠습니다.

STEP 1

같은 SQL 재현

동일한 스키마와 행을 여러 Storage에서 실행해 입력 조건을 맞춥니다.

STEP 2

코드 계약 추적

각 구현이 어떤 trait을 어떻게 구현하고 테스트하는지 파일 단위로 확인합니다.

STEP 3

차이를 문서화

재시작, 데이터 경로, 지원 동작, 오류를 명령과 결과가 있는 예제로 남깁니다.

STEP 4

작은 빈틈 제안

검증 과정에서 확인된 문서 누락, 테스트 공백, 작은 사용성 문제부터 논의합니다.

공개 이슈 #1408의 Storage 기능 비교 요구는 이 작업의 필요성을 보여주지만, 지금 당장 맡겠다는 선언은 아니다.
제가 생각한 기여 접근은 네 단계입니다. 먼저 같은 SQL을 여러 Storage에서 재현하고, 각 구현의 trait과 테스트를 읽고, 차이를 실행 가능한 문서로 정리합니다. 그 과정에서 확인된 작은 누락부터 Maintainer와 논의하려고 합니다. #1408에는 Storage별 지원 기능을 비교해 달라는 요구가 이미 있지만 범위가 큽니다. 그래서 이슈 전체를 맡겠다고 하기보다 작은 비교 단위로 나눌 수 있는지 근거를 먼저 만들겠습니다. [Sources] https://github.com/gluesql/gluesql/issues/1408
