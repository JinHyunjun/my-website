GlueSQL에서 데이터는 어디에 남을까?

지금까지의 학습, Storage에 관심을 갖게 된 경험, Issue #1408과 비교 문서 계획을 13장에 맞춰 설명하는 발표 대본입니다.

배운 것

SQL Core와 Storage가 역할과 trait으로 분리되어 있다.

관심 영역

데이터의 저장 방식과 상황에 맞는 Storage 선택

기여 접근

#1408을 바탕으로 실행 가능한 Storage 비교 문서 만들기

발표의 선: #1408은 관심과 연결된 기존 요구입니다. 아직 맡겠다는 선언은 아니며, 일부 Storage를 직접 검증해 기여 범위를 제안하는 단계입니다.

Slide 01 · 표지약 40초

질문과 발표 순서를 한 번에 제시하기

안녕하세요, 진현준입니다. 저는 지금까지 GlueSQL의 SQL 실행 흐름을 따라가며 CLI로 직접 데이터를 만들고 조회했습니다. 그 과정에서 같은 SQL을 실행해도 어떤 Storage를 선택하느냐에 따라 데이터가 남는 방식이 달라진다는 점이 가장 궁금해졌습니다. 오늘은 무엇을 배웠는지, 왜 Storage에 관심을 갖게 되었는지, 이 관심을 어떤 기여 방식으로 발전시키고 싶은지 말씀드리겠습니다.

첫 문장에서 “Storage가 관심 영역”이라는 결론을 보여주고, 특정 이슈 이야기는 꺼내지 않습니다.

Slide 02 · 지금까지 한 일약 50초

학습을 실행 순서로 설명하기

처음에는 Rust 프로젝트를 어떻게 실행하는지도 낯설었습니다. Rust와 Cargo 환경을 준비하고 예제를 컴파일한 뒤, CLI에서 CREATE, INSERT, SELECT, UPDATE, DELETE를 직접 실행했습니다. 이어서 MemoryStorage와 SledStorage로 같은 테이블을 열어 데이터가 재실행 뒤에도 남는지 비교했습니다. 최근에는 Translator의 table function 인자 처리를 읽고 관련 테스트도 실행했습니다. 아직 upstream PR은 없지만, 동작을 재현하고 코드 위치를 찾아 질문할 수 있는 단계까지 왔습니다.

성과를 과장하지 않고 “실행 기반을 만들었다”는 점에 힘을 줍니다.

Slide 03 · 배운 실행 흐름약 55초

각 단계를 한 문장씩 연결하기

제가 이해한 기본 흐름은 SQL, Parser, Translator, Planner, Executor, Storage, Payload입니다. Parser는 SQL을 AST로 만들고, Translator는 이를 GlueSQL이 사용하는 문장으로 바꿉니다. Planner는 Storage와 실행할 계획을 만들고 Executor가 실제 연산을 수행합니다. 이때 Storage는 스키마와 원본 행을 제공하거나 변경을 반영합니다. 마지막 Payload가 조회 결과나 변경 건수를 호출자에게 돌려줍니다. 중요한 점은 Storage가 SELECT 결과를 따로 쌓는 곳은 아니라는 것입니다.

Storage와 Payload를 분리해서 말합니다. 이 구분이 다음 슬라이드의 경험으로 이어집니다.

Slide 04 · 관심이 생긴 순간약 55초

실제 실패 경험을 관심의 출발점으로 말하기

Storage에 관심을 갖게 된 직접적인 계기는 CLI를 종료했다가 다시 열었을 때 테이블이 사라진 경험입니다. 기본 실행은 MemoryStorage이므로 데이터가 그 프로세스의 메모리에만 있었습니다. 이후 --storage sled와 --path를 지정해 실행하자 같은 경로에서 테이블과 행을 다시 조회할 수 있었습니다. 이때 컴파일 결과인 target 폴더와 실제 DB 데이터가 별개라는 점도 이해했습니다. 같은 SQL인데 데이터 생명주기가 달라진 이유가 제 다음 질문이 됐습니다.

명령 전체를 읽지 말고 Memory, Sled, path 세 단어만 짚습니다.

Slide 05 · Storage 코드 계약약 55초

trait을 인터페이스 계약으로 설명하기

코드에서는 core/src/store.rs가 Storage 경계를 정의합니다. Store는 스키마와 행을 읽는 메서드를, StoreMut은 데이터를 추가하거나 삭제하는 메서드를 정의합니다. GStore와 GStoreMut은 Index, Metadata, Transaction 같은 여러 trait을 조합합니다. 각 Storage가 이 계약을 구현하기 때문에 Core는 Memory나 Sled 같은 특정 구현에 직접 묶이지 않습니다. 그래서 같은 SQL 실행 Core에 서로 다른 저장 방식을 끼울 수 있습니다.

Rust 문법을 길게 설명하지 말고 “Core가 요구하는 기능 목록”이라고 풀어 말합니다.

Slide 06 · 선택 기준약 50초

최고의 Storage가 아니라 조건의 조합이라고 말하기

Storage 선택은 어느 하나가 항상 더 좋다는 문제가 아니라고 생각합니다. 첫째, 데이터가 프로세스 안에서만 필요할지 재시작 뒤에도 남아야 할지 봐야 합니다. 둘째, 브라우저나 로컬 앱, 여러 스레드, 외부 서비스처럼 실행 환경을 봐야 합니다. 셋째, JSON이나 CSV처럼 기존 파일 형식과 연결할 필요가 있는지 확인해야 합니다. 넷째, 인덱스, 트랜잭션, 스키마 변경 같은 기능 요구가 있습니다. 이 네 조건을 코드와 테스트로 확인하는 것이 제 관심입니다.

각 기준을 짧게 끊고, 아직 성능 우열을 주장하는 것이 아니라고 분명히 합니다.

Slide 07 · Storage 지형약 65초

12개 이름을 외우기보다 분류의 목적을 설명하기

현재 storages 디렉터리에는 12개 crate가 있습니다. Memory와 SharedMemory는 메모리 사용을, Sled와 Redb와 File은 로컬 영속 저장을 먼저 떠올릴 수 있습니다. JSON, CSV, Parquet은 파일 형식과 연결되고, Mongo와 Redis는 외부 서비스, Composite와 Git은 조합과 변경 이력이라는 질문으로 볼 수 있습니다. 이 분류는 공식 우열표가 아니라 제가 탐색하기 위한 질문 지도입니다. 현재 CLI에서는 Memory, Sled, Redb, JSON, CSV, Parquet, File 일곱 종류를 직접 선택할 수 있습니다.

Storage 이름을 전부 빠르게 읽은 뒤, “CLI에서 직접 비교할 수 있는 7개”로 초점을 좁힙니다.

Slide 08 · 나의 관심 영역약 45초

관심을 한 문장과 세 질문으로 고정하기

그래서 제 관심을 한 문장으로 정리했습니다. 같은 SQL을 유지하면서 사용 목적에 맞는 Storage를 어떻게 선택하고 검증할 수 있을까?입니다. 이를 위해 각 Storage가 데이터를 어디에 어떤 형태로 남기는지, 같은 SQL에서 지원 기능과 오류 경계가 어떻게 다른지, 초보자가 선택할 수 있는 설명이 충분한지를 확인하고 싶습니다. 단순히 Storage 이름을 나열하는 문서보다 실제 명령과 결과가 있는 비교를 만들고 싶습니다.

큰 인용문을 천천히 읽고, 아래 세 상자는 키워드만 짚습니다.

Slide 09 · 다른 기여 방향약 45초

다른 팀원의 방향과 비교하되 우열을 만들지 않기

팀원 중에는 GlueSQL에 아직 구현되지 않은 SQL 문법이나 함수를 추가하는 데 관심이 있는 분들도 있습니다. 그 방향은 사용자가 무엇을 표현할 수 있는지를 넓힙니다. 제가 관심을 가진 Storage 방향은 데이터가 어디에서 어떻게 살게 할지를 다룹니다. 둘 중 하나가 더 중요하다는 뜻은 아닙니다. GlueSQL의 모듈성을 서로 다른 쪽에서 확장하는 기여입니다. 현재 저는 새로운 문법보다 같은 SQL과 다른 Storage의 차이에서 더 많은 질문이 생겼습니다.

오른쪽 Storage 패널에서 “현재의 나”라는 표현을 사용합니다.

Slide 10 · 기존 이슈약 65초

개인적인 관심이 실제 프로젝트 요구와 만났다고 설명하기

제 관심과 거의 같은 문제를 이미 #1408이 제기하고 있었습니다. 2023년 9월 gitmalong이 등록했고 현재 Open이며 Assignee와 연결 PR은 없습니다. 이슈의 내용은 새 프로젝트에서 먼저 Storage를 선택해야 하지만 backend별 지원 기능을 알기 어려우므로 비교표가 필요하다는 것입니다. 저는 기능 지원표에 더해 CLI 명령, 데이터 경로, 재실행 결과, 코드와 테스트 근거까지 연결해 보고 싶습니다. 새로운 중복 이슈를 만들기보다, 일부 Storage부터 검증해 #1408을 실행 가능한 문서로 구체화하는 방향을 먼저 논의하겠습니다.

이슈 번호, 현재 상태, 기존 요구, 내가 더할 부분 순으로 설명합니다.

Slide 11 · 비교 문서약 60초

추천표가 아니라 판단과 재현을 돕는 문서라고 말하기

비교 문서에는 다섯 가지를 기록하겠습니다. 첫째, 종료와 재실행 뒤 데이터가 남는지 확인합니다. 둘째, 메모리, 단일 파일, 디렉터리, 외부 서비스 중 데이터 위치와 형식을 기록합니다. 셋째, StoreMut, Transaction, Index, AlterTable 같은 지원 기능을 trait과 test-suite로 확인합니다. 넷째, Rust와 WASM 또는 외부 서비스 같은 실행 조건을 적습니다. 마지막으로 동일 결과를 재현할 CLI 명령, SQL, 출력과 오류를 연결합니다. 아직 확인하지 않은 항목은 추측하지 않고 실험 예정으로 표시하겠습니다.

슬라이드 아래의 비교 문서 링크는 발표 후 공유할 실제 산출물이라고 설명합니다.

Slide 12 · CLI 명령약 65초

일곱 Storage를 같은 입력으로 비교하는 출발점을 제시하기

현재 CLI에서 직접 선택할 수 있는 Storage는 Memory, Sled, Redb, JSON, CSV, Parquet, File 일곱 개입니다. Memory는 옵션 없이 실행하고, 나머지는 --storage와 --path를 함께 지정합니다. Redb는 단일 데이터베이스 파일을 경로로 받고, Sled와 파일 기반 Storage는 작업 디렉터리를 사용합니다. 각 명령으로 같은 CREATE, INSERT, SELECT를 실행하고 종료한 뒤 같은 명령으로 다시 열겠습니다. 그다음 SELECT 결과와 실제로 생성된 파일을 함께 기록하겠습니다. 전체 절대 경로 명령은 별도 비교 문서에서 그대로 실행할 수 있습니다.

명령을 전부 읽지 말고 Memory의 예외, storage+path 규칙, Redb 단일 파일만 강조합니다.

Slide 13 · 결론약 45초

학습, 관심, 기존 이슈, 산출물을 연결하기

정리하겠습니다. 저는 GlueSQL의 SQL 실행 흐름을 CLI와 코드로 따라가며 기본 구조를 배웠고, Memory와 Sled의 차이에서 데이터 생명주기와 Storage 선택에 관심을 갖게 됐습니다. 이 관심은 #1408의 Storage 기능 비교 요구와 연결됩니다. 앞으로는 CLI에서 선택할 수 있는 Storage부터 같은 조건으로 실행하고, 선택 기준과 실제 동작을 비교 문서에 남기겠습니다. 그 근거를 가지고 #1408의 일부 범위에 기여할 수 있는지 Maintainer와 논의하겠습니다. 감사합니다.

예상 질문과 답변

Q. GlueSQL은 데이터베이스인가요?

A. MySQL처럼 독립 서버 하나로만 보는 것보다, 애플리케이션에 넣어 SQL 실행 Core와 원하는 Storage를 조합하는 임베디드 SQL 엔진으로 이해하는 편이 정확합니다.

Q. 어떤 Storage가 가장 좋나요?

A. 하나의 정답을 전제하지 않습니다. 영속성, 실행 환경, 데이터 형식, 필요한 기능을 먼저 정하고 실제 구현과 테스트로 적합성을 확인해야 합니다.

Q. Storage를 새로 구현하겠다는 뜻인가요?

A. 아직 아닙니다. 먼저 기존 Storage들을 같은 조건으로 실행해 계약과 차이를 이해하고, 그 과정에서 발견한 문서나 테스트의 작은 빈틈부터 기여하려고 합니다.

Q. 그러면 #1408을 바로 맡겠다는 뜻인가요?

A. 아직 아닙니다. 이슈 전체는 12개 Storage와 여러 기능을 다뤄 범위가 큽니다. CLI에서 선택 가능한 일부 Storage부터 검증한 뒤, 부분 기여가 가능한지 Maintainer에게 먼저 확인합니다.

Q. 왜 SQL 문법보다 Storage인가요?

A. CLI에서 데이터가 사라지고 다시 남는 차이를 직접 겪으면서 데이터 생명주기와 저장 방식에 더 구체적인 질문이 생겼기 때문입니다.

Q. 비교 결과는 어떤 형태로 남길 건가요?

A. 동일 SQL, 실행 명령, 재실행 결과, 데이터 경로, 오류 출력, 관련 코드 위치를 함께 기록한 재현 가능한 표와 예제로 남길 계획입니다.
