SQL 한 줄은 GlueSQL 안에서 어떻게 읽힐까?

슬라이드 12장에 맞춘 발표 대본입니다. 문장을 전부 외우기보다 각 장의 첫 문장과 강조 문장만 익히면 자연스럽게 이어집니다.

오늘의 주장

특정 이슈보다 먼저 기여 방식을 정했다.

기여 방식

재현 → 테스트 → 설명 → 작은 코어 변경

말하지 않을 것

아직 맡지 않은 기능을 기여하겠다고 선언하지 않는다.

2026년 7월 31일 기준: 최근 main 변경도 지원하지 않는 CREATE TABLE 옵션을 Translator 오류로 명확히 하고 unit test와 SQL fixture를 함께 추가했습니다. 이 패턴을 내 첫 기여 방식의 참고 사례로 삼되, 해당 이슈를 맡겠다는 뜻은 아닙니다.

Slide 01 · 표지 약 30초

발표의 범위를 먼저 제한하기

안녕하세요, 진현준입니다. 저는 아직 어떤 이슈에 기여하겠다고 결정하지 않았습니다. 오늘은 그 결정을 억지로 내리는 대신, SQL 한 줄이 GlueSQL 내부에서 어떻게 읽히는지를 따라가며 제가 어떤 방식으로 첫 기여를 준비할지 말씀드리겠습니다. 출발점은 GLUE_TABLES(1)이라는 작은 SQL과 Rust의 args 파라미터였습니다.

첫 문장에서 “이슈 발표가 아니다”를 분명히 말하고 다음 장으로 이동합니다.

Slide 02 · 관심의 출발점 약 40초

관심 분야 대신 반복한 질문을 보여주기

처음에는 GlueSQL이 데이터베이스인지, Storage를 바꾸면 왜 데이터가 남는지 같은 기본 질문부터 시작했습니다. 그다음 Parser와 Translator가 왜 나뉘는지, 코드의 언더스코어를 None으로 바꾸면 왜 동작이 달라지는지가 궁금해졌습니다. 질문들을 모아 보니 저는 Storage 구현 자체보다, 사용자가 입력한 SQL의 의미가 Rust 자료구조로 옮겨지는 과정에 더 관심이 있다는 것을 알게 됐습니다.

오른쪽 질문 세 개를 위에서 아래로 짚습니다.

Slide 03 · 전체 흐름 약 55초

아는 범위와 아직 모르는 범위를 구분하기

GlueSQL CLI에 SQL 문자열을 입력하면 Parser가 먼저 sqlparser의 AST를 만듭니다. Translator는 그 AST를 GlueSQL이 사용하는 내부 AST로 옮기면서 지원하지 않는 구조를 거절합니다. Planner는 Storage의 스키마와 실행 문맥을 이용해 식과 참조를 검증하고 실행 가능한 계획으로 낮춥니다. Executor는 그 계획에 따라 Storage에서 원본 데이터를 읽거나 변경하고, 마지막에 Payload를 반환합니다. 여기서 Planner를 MySQL의 비용 기반 옵티마이저와 완전히 같은 것으로 이해하면 안 됩니다. 이번 발표에서 제가 실제로 확인한 범위는 Parser와 Translator의 경계까지입니다.

파이프라인을 왼쪽에서 오른쪽으로 한 번 훑고, Parser와 Translator에서 잠깐 멈춥니다.

Slide 04 · 세 입력 비교 약 45초

겉모양은 같아도 의미가 다름을 설명하기

SERIES(3)은 GlueSQL이 지원하는 table function이라 숫자 3을 실제 크기로 사용합니다. 반면 GLUE_TABLES는 메타데이터를 보여 주는 dictionary table이라 인자를 받을 이유가 없습니다. 일반 테이블인 Foo도 함수처럼 호출하는 기능은 지원하지 않습니다. 세 SQL 모두 괄호 모양은 비슷하지만, GlueSQL이 허용해야 하는 입력은 첫 번째뿐입니다. 제가 본 기존 코드에서는 나머지 입력의 인자가 조용히 사라질 수 있었습니다.

“괄호가 같다고 기능이 같은 것은 아니다”를 강조합니다.

Slide 05 · args 약 45초

Rust의 Option을 SQL 모양과 연결하기

args의 타입은 Option<TableFunctionArgs>입니다. 그래서 괄호가 없으면 None, 괄호가 있으면 Some으로 표현됩니다. 여기서 중요한 점은 숫자 1이나 3의 값뿐 아니라, 인자가 존재한다는 사실 자체가 이미 SQL의 의미라는 것입니다. Translator는 테이블 이름과 이 존재 여부를 함께 보고 dictionary인지, 지원되는 function인지, 거절할 입력인지 구분할 수 있습니다.

표의 None과 Some 열을 번갈아 가리킵니다.

Slide 06 · 원인 약 45초

언더스코어 자체가 문제가 아님을 분명히 하기

Rust의 match에서 언더스코어는 어떤 값이 와도 받겠다는 뜻입니다. 따라서 ("GLUE_TABLES", _)는 None뿐 아니라 Some(1)도 받습니다. 문제는 언더스코어 문법 자체가 아니라, 이 위치에서 GlueSQL의 기능 계약보다 넓은 입력을 허용했다는 점입니다. 이후 Dictionary AST에는 인자를 저장할 필드가 없기 때문에 입력 정보가 사라집니다. 즉, Parser가 읽을 수 있는 SQL과 GlueSQL이 지원하는 SQL은 다릅니다.

마지막 강조 문장은 천천히 말합니다.

Slide 07 · 로컬 실험 약 45초

기여가 아니라 학습 실험이라고 선 긋기

로컬 학습 브랜치에서는 Dictionary가 None일 때만 통과하도록 바꾸고, 처리되지 않은 Some은 명시적인 TranslateError로 보내 봤습니다. 그리고 괄호가 비어 있거나 값이 있는 경우를 테스트에 추가했습니다. 테스트는 통과했지만 이것을 바로 PR로 만들지는 않았습니다. 요구사항의 우선순위와 다른 작업과의 관계를 확인하지 않았기 때문입니다. 이 변경의 가치는 코드를 제출한 것보다 입력과 내부 표현의 경계를 직접 검증한 것에 있습니다.

“현재 로컬 실험이며 제출하지 않았다”를 빠뜨리지 않습니다.

Slide 08 · 오류 단계 약 45초

ParserError와 TranslateError를 한 문장으로 구분하기

DELECT는 SQL 문법에 없는 단어이므로 Parser가 AST를 만들지 못하고 ParserError가 납니다. 반면 GLUE_TABLES(1)은 sqlparser가 표현할 수 있는 SQL 구조이지만 GlueSQL에는 그런 기능이 없으므로 Translator가 거절해야 합니다. SERIES(3)은 지원되는 입력이라 이후 Planner와 Executor로 이동합니다. 정리하면 문장 자체를 읽지 못하면 Parser, 읽었지만 GlueSQL의 지원 범위가 아니면 Translator입니다.

세 줄의 멈추는 위치를 차례대로 보여 줍니다.

Slide 09 · 학습 경계 약 40초

모르는 것을 숨기지 않고 다음 기준으로 바꾸기

이 실험으로 args, match 순서, 오류 단계는 설명할 수 있게 됐습니다. 하지만 Planner 이후의 세부 호출과 프로젝트가 테스트를 나누는 기준은 아직 더 읽어야 합니다. 그래서 하나를 이해했다고 특정 기여 이슈를 선언하지 않겠습니다. 대신 저는 기능보다 먼저 기여 방식을 정하기로 했습니다. 재현 가능한 근거를 만들고, 테스트를 읽고, 다른 사람이 이해할 수 있게 설명하는 방식입니다.

왼쪽은 배운 것, 오른쪽은 다음 학습이라는 구조만 간단히 짚습니다.

Slide 10 · 기여 방식 약 55초

발표의 핵심 결론을 말하기

제가 선택한 첫 기여 방식은 문서와 테스트 우선입니다. 먼저 SQL 한 줄을 CLI에서 누구나 재현할 수 있게 입력, 실제 결과, 기대 결과를 적습니다. 다음으로 가장 가까운 SQL fixture를 찾아 이미 어떤 동작을 보장하는지 읽습니다. 마지막으로 초보자가 막히지 않도록 동작 이유를 문서나 예제로 설명합니다. 코어 코드는 이 세 가지 근거가 준비되고 프로젝트 방향을 확인한 뒤 필요한 만큼만 바꾸겠습니다. 문서와 테스트는 준비 운동이 아니라 동작 계약을 명확히 하는 실제 기여입니다.

“문서와 테스트도 실제 기여”를 확실하게 말합니다.

Slide 11 · 실행 계획 약 50초

발표 이후 무엇을 할지 구체적으로 말하기

발표 이후에는 한 SQL 사례로 이 작은 루프를 완주하겠습니다. 먼저 궁금한 동작을 하나 고르고, SledStorage를 포함한 실행 조건과 CLI 출력을 남깁니다. 그다음 관련 fixture를 읽고 Parser, Translator, Planner 중 어느 단계가 책임지는지만 좁게 추적합니다. 마지막에는 재현 결과와 예상 범위를 팀에 먼저 공유하겠습니다. 이렇게 하면 이미 작업 중인 PR과 겹치는 것을 피하고, 문서 수정인지 테스트 보강인지도 근거를 가지고 결정할 수 있습니다.

다섯 단계의 영문 키워드만 차례로 읽어도 흐름이 살아납니다.

Slide 12 · 결론 약 35초

“미정”이 아니라 “방식 결정”으로 끝내기

정리하겠습니다. 저는 아직 맡을 이슈를 정하지 않았습니다. 대신 SQL 한 줄을 기준으로 실행 흐름을 세로로 읽고, 재현 기록과 fixture 테스트, 초보자 관점의 문서를 먼저 만드는 기여 방식을 정했습니다. 그리고 이해와 합의가 생긴 범위에서만 작은 코어 변경으로 확장하겠습니다. 이번 발표는 기여 대상을 고른 결과가 아니라, 겹치지 않고 배우면서 기여하는 기준을 만든 과정입니다. 감사합니다.

마지막 문장 뒤에 한 박자 쉬고 “질문 부탁드립니다”라고 덧붙입니다.

용어 메모

AST
SQL 문자열을 프로그램이 다룰 수 있도록 구조화한 트리입니다.
Translator
sqlparser AST를 GlueSQL 내부 표현으로 옮기며 지원 범위를 확인합니다.
Fixture
SQL 입력과 기대 Payload 또는 오류를 한 파일에 적은 회귀 테스트 사례입니다.
Payload
SELECT 결과, 생성·수정 행 수처럼 실행 뒤 사용자에게 돌아오는 결과입니다.

예상 질문과 답변

Q. 그래서 정확히 어떤 기능에 기여할 예정인가요?

A. 아직 기능은 정하지 않았습니다. 먼저 한 SQL 사례의 재현, fixture 확인, 책임 단계 추적을 완료한 뒤 팀과 겹치지 않는 문서나 테스트 범위를 정하겠습니다.

Q. 문서와 테스트도 충분한 오픈소스 기여인가요?

A. 네. SQL fixture는 지원 동작과 오류를 고정해 회귀를 막고, 문서는 사용자와 다음 기여자가 같은 동작을 재현하게 합니다. 둘 다 코드의 계약을 명확히 합니다.

Q. 왜 GLUE_TABLES(1)은 ParserError가 아닌가요?

A. sqlparser가 테이블 함수 모양으로 AST를 만들 수 있기 때문입니다. 문법 구조는 유효하지만 GlueSQL이 지원하지 않으므로 Translator 오류가 알맞습니다.

Q. 최근 main 업데이트와 이번 발표는 어떤 관계인가요?

A. 최근 변경도 지원하지 않는 CREATE TABLE 옵션을 Translator에서 명시적으로 거절하고 unit test와 SQL fixture를 함께 추가했습니다. 제가 맡을 작업은 아니지만, 재현에서 오류 계약과 테스트로 이어지는 좋은 참고 사례입니다.
