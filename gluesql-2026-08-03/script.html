막막함에서 후보를 좁힌 과정이라고 소개하기

안녕하세요, 진현준입니다. 지난 발표자료에서는 아직 무엇에 기여할지 모르겠다는 이야기가 중심이었습니다. 이번에는 거기서 한 단계 더 나아가, 제가 실제로 실행한 경험을 기준으로 만들고 현재 GitHub 후보들을 비교했습니다. 그 결과 첫 탐색 대상으로 좁힌 항목과 그 이유를 말씀드리겠습니다. 아직 이슈를 맡았거나 PR을 준비 중이라는 뜻은 아닙니다.

“첫 탐색 후보”와 “확정 기여”를 처음부터 구분합니다.

Slide 02 · 실행 근거 약 50초

이미 한 일을 숫자와 연결하기

먼저 제가 어디까지 왔는지 정리했습니다. MemoryStorage와 SledStorage를 비교해 프로세스 종료와 데이터 영속성의 차이를 확인했고, CLI에서 CRUD 다섯 동작을 실행했습니다. table function 인자 경계를 로컬 학습 브랜치에서 수정해 보면서 Core 테스트 515개와 MemoryStorage fixture 196개를 통과시켰고 Clippy와 Formatter도 확인했습니다. 이 로컬 변경 자체를 기여 주제로 밀지는 않겠습니다. 대신 코드를 읽고 테스트로 검증할 수 있다는 근거로 사용했습니다.

네 개 숫자를 왼쪽부터 읽고 로컬 실험의 위치를 분명히 합니다.

Slide 03 · 선정 기준 약 50초

good first issue보다 구체적인 기준을 말하기

초보자에게 쉬운 이슈가 무엇인지 판단하기 위해 네 가지 기준을 만들었습니다. 첫째, CLI나 테스트로 현재 동작을 직접 재현할 수 있어야 합니다. 둘째, 변경할 파일과 책임 경계를 설명할 수 있을 만큼 범위가 작아야 합니다. 셋째, 따라갈 기존 테스트나 문서가 있어야 합니다. 넷째, Assignee뿐 아니라 댓글과 활성 PR까지 확인해 다른 사람의 작업과 겹치지 않아야 합니다. 코드 줄 수보다 불확실성이 얼마나 작은가를 본 것입니다.

네 기준을 각각 한 문장으로 끊어 말합니다.

Slide 04 · 기여 난이도 지도 약 45초

문서부터 시작하는 이유를 낮은 가치로 설명하지 않기

GlueSQL 기여는 문서, 테스트와 예제, fixture 도구, Core 기능 변경으로 난이도가 올라갑니다. 첫 PR은 문서나 테스트에서 시작해도 충분합니다. 다만 문서를 단순 번역하거나 추측으로 쓰는 것은 아닙니다. 실제 Query Builder API를 실행하고 Payload를 확인한 뒤 그 결과를 설명해야 합니다. 그래서 문서와 테스트는 코어보다 덜 중요한 일이 아니라, 현재 동작을 이해했다는 검증 가능한 산출물입니다.

왼쪽에서 오른쪽으로 난이도가 높아진다는 점만 짚습니다.

Slide 05 · 후보 비교 약 70초

왜 다른 후보를 지금 선택하지 않았는지 설명하기

현재 열린 후보 다섯 개를 비교했습니다. #1408의 Storage 기능 표는 제 Memory와 Sled 경험과 잘 맞지만 모든 Storage의 trait 지원 여부를 검증해야 해서 범위가 큽니다. #1946은 빈 SELECT에서 type assertion이 통과하는 문제인데, 어떤 동작을 정답으로 할지 합의가 먼저입니다. #1947은 fixture 표 안의 세로 막대를 처리하는 문제로 escape 규칙과 이전 파일의 호환성을 설계해야 합니다. #1011은 good first issue지만 기존에 진행 의사를 밝힌 댓글이 있습니다. 이에 비해 #1676의 Data Injection은 Todo, 기존 예제, 작은 파일 범위, 낮은 중복 위험을 함께 갖췄습니다.

모든 후보를 자세히 읽기보다 마지막 비교 문장에 힘을 줍니다.

Slide 06 · 추천 후보 약 55초

#1676 전체가 아닌 하위 항목 하나라고 강조하기

#1676은 Query Builder 문서 Todo가 여러 개 묶인 큰 이슈입니다. 제가 보는 것은 그 전체가 아니라 Data Injection 한 항목입니다. 해당 문서는 현재 제목과 Todo, VALUES 한 줄만 있습니다. 반면 Core의 values 구현과 test-suite의 기존 예제가 있어 따라갈 선례가 있습니다. 활성 문서 PR #1935도 이 페이지를 수정하지 않습니다. 다만 미할당이라는 사실만으로 바로 시작하지 않고, Data Injection 하위 항목만 진행해도 되는지 먼저 확인하겠습니다.

“추천은 구현 시작이 아니라 확인할 가치가 가장 높다는 뜻”이라고 덧붙입니다.

Slide 07 · 변경 지도 약 55초

파일 네 개의 역할로 범위를 설명하기

기존 패턴을 보면 예상 변경 범위는 네 역할로 나뉩니다. 첫째, Data Injection 테스트 파일을 추가해 values(...).execute(glue)의 입력과 Payload를 검증합니다. 둘째, querying 모듈에 새 테스트를 공개합니다. 셋째, test-suite의 공통 Storage 테스트에 등록합니다. 넷째, 검증된 코드와 결과 표로 Todo 문서를 교체합니다. 계획상 Core 수정은 없습니다. 새 테스트 하나, 등록 두 곳, 문서 한 페이지라서 리뷰 가능한 범위입니다.

각 상자의 파일명보다 아래 역할을 먼저 말합니다.

Slide 08 · 실행 경로 약 55초

이 기여 후보가 무엇을 새로 가르치는지 설명하기

이 후보가 좋은 또 하나의 이유는 제가 아는 GlueSQL 흐름을 확장해 주기 때문입니다. SQL 문자열은 Parser와 Translator를 지나 StatementPlan으로 갑니다. Query Builder는 Rust API의 Build 구현으로 StatementPlan을 직접 만들고, 그다음 Storage Planner와 Executor로 들어갑니다. 즉 Parser와 Translator를 거치지 않는 두 번째 입력 경로입니다. 문서와 테스트를 작성하면서 Query Builder가 같은 실행기로 합류하는 지점을 실제 코드로 확인할 수 있습니다.

Parser·Translator에 취소선이 있는 이유를 꼭 설명합니다.

Slide 09 · 중복 방지 약 50초

확인 절차를 기여 활동의 일부로 말하기

실제 코드를 쓰기 전에는 세 번 확인합니다. 이슈의 Assignee, 최근 댓글, 연결 PR을 보고, 활성 PR이 수정하는 정확한 파일 목록도 비교합니다. 마지막으로 이슈에 Data Injection 한 항목의 테스트와 문서를 진행해도 되는지 묻습니다. 답변 전에는 기존 테스트 실행과 코드 읽기까지만 합니다. 이렇게 해야 미할당 이슈라도 누군가 준비 중인 작업과 겹치는 위험을 줄일 수 있습니다. 질문은 막혀서 하는 일이 아니라 범위를 합의하는 기여 절차입니다.

영문 댓글 예시는 읽지 말고 질문의 핵심만 한국어로 말합니다.

Slide 10 · 다음 실행 순서 약 55초

발표 후 바로 할 일을 실행 단위로 말하기

다음 순서는 다섯 단계입니다. 먼저 기존 values 테스트를 실행해 현재 API와 Payload를 확인합니다. 다음으로 완성된 Data Aggregation 문서와 테스트를 비교해 프로젝트 문서 형식을 익힙니다. 그 뒤 최소 예제의 입력과 기대 결과를 한 문장으로 정하고, #1676에 범위를 질문합니다. 합의되면 별도 기여 브랜치에서 구현하고, 이미 겹치거나 범위가 커지면 #1408 Storage 문서의 더 작은 조사 단위로 전환합니다. 진행 기준뿐 아니라 중단과 전환 기준도 미리 정했습니다.

Run, Read, Define, Ask, Decide 순으로 손가락을 이동합니다.

Slide 11 · 중간보고서 약 50초

기여 건수와 준비 성과를 분리해 보고하기

중간보고서에는 upstream PR 0건을 그대로 적겠습니다. 대신 환경 구축, CRUD, Memory와 Sled 비교, Core 테스트 515개, fixture 196개, 로컬 학습 브랜치와 후보 다섯 개 비교를 증거로 남깁니다. 완료한 일과 아직 하지 않은 일을 구분하고, Sled 재시작 화면, 테스트 통과 화면, 모임 증빙을 추가하겠습니다. 이렇게 하면 “아직 기여하지 못했다”가 아니라 기여할 수 있는 상태를 어떻게 만들었는지를 보여줄 수 있습니다.

PR 0건을 작게 말하지 말고 솔직한 현재 상태로 말합니다.

Slide 12 · 결론 약 35초

후보는 구체적으로, 약속은 신중하게 끝내기

정리하겠습니다. 저는 실행 경험을 기여 판단의 근거로 바꿨고, 재현성, 범위, 선례, 중복이라는 기준으로 후보를 비교했습니다. 그 결과 #1676의 Data Injection 문서와 Query Builder 테스트를 첫 탐색 대상으로 좁혔습니다. 아직 확정 기여는 아닙니다. 기존 테스트를 실행하고 Maintainer에게 범위를 확인한 뒤 다음 결정을 내리겠습니다. 막막함에서 검증 가능한 후보까지 왔다는 것이 이번 발표의 결론입니다. 감사합니다.

한 박자 쉬고 “질문 부탁드립니다”로 마칩니다.

용어 메모

Query Builder
SQL 문자열 대신 Rust API를 조합해 GlueSQL의 실행 계획을 만드는 인터페이스입니다.
StatementPlan
Planner와 Executor가 사용할 수 있도록 표현식과 문장을 실행 가능한 형태로 담은 구조입니다.
Fixture
SQL 입력과 기대 Payload 또는 오류를 함께 기록한 회귀 테스트 자산입니다.
Payload
SELECT 결과, 생성·수정 행 수처럼 실행 뒤 호출자에게 돌아오는 결과입니다.

예상 질문과 답변

Q. 그래서 #1676에 기여하겠다는 뜻인가요?

A. 아직 확정이 아닙니다. Data Injection 한 항목을 첫 탐색 대상으로 정했고, 기존 테스트 실행과 Maintainer의 범위 확인 후에만 구현을 시작합니다.

Q. Data Injection은 정확히 무엇인가요?

A. Query Builder의 values(...)를 사용해 테이블 없이 값 행을 직접 만들고 실행하는 사용법입니다. SQL의 VALUES (1, 'Jin')에 대응합니다.

Q. Parser와 Translator를 공부했는데 왜 Query Builder로 바꿨나요?

A. 바꾼 것이 아니라 학습 범위를 확장한 것입니다. Query Builder도 결국 Storage Planner와 Executor에 합류하므로, 기존 지식을 활용하면서 새로운 입력 경로를 배울 수 있습니다.

Q. 왜 #1408 Storage 문서를 먼저 하지 않나요?

A. 개인 경험과는 잘 맞지만 정확한 기능 표를 만들려면 여러 Storage trait과 테스트를 전부 검증해야 합니다. 첫 PR로는 범위가 크고, 더 작은 하위 조사로 쪼갤 합의가 필요합니다.

Q. upstream PR이 0건인데 중간보고서에 쓸 것이 충분한가요?

A. 기여 건수는 0건으로 명확히 적습니다. 대신 재현 가능한 실행 기록, 테스트 수치, 로컬 실험, 이슈 중복 조사, 다음 후보의 파일 범위를 정량 근거로 제시합니다.
